# Trunk flow

How a change reaches the captain's users, for every project registered `local-trunk`, in every home. `bin/jg-trunk.sh` owns each step; its header is the command reference, and `bin/jg-trunk-policy-lib.sh` holds every open captain call with its safe default (override in `config/trunk-policy`).

## Scope: local-trunk projects only

The trunk flow is a fourth delivery posture, `local-trunk` (`data/projects.md`: `- <name> [local-trunk] - ...`). **Every rule below applies to a project registered local-trunk and to no other.** A project registered `no-mistakes`, `direct-PR` or `local-only` (or not registered) keeps its own rules exactly as before: `direct-PR` still pushes and opens its PR, `no-mistakes` still runs its pipeline, `local-only` still stops at a ready branch and is merged locally by `bin/jg-merge-local.sh`. Each trunk entry point reads the project's registered mode first and refuses or ignores any other: every `jg-trunk.sh` subcommand refuses it naming the registered mode, the landing check skips it, the spawn refusal and the lane brief section apply only to local-trunk, and no trunk hook is installed in it. `tests/jg-trunk-scope.test.sh` proves one case per mode and fails if any of them is treated as local-trunk.

In a local-trunk project the lanes ship as `local-trunk` tasks (nothing is pushed), and both normal and `--raw` output from `bin/jg-project-mode.sh` retain `local-trunk`.
Pass `--mode local-trunk` to the brief, spawn and Recon promotion; the generated delivery contract, recorded task mode and completion receipt retain that identity.
Existing in-flight `mode=local-only` tasks remain accepted by the trunk lander and landing check only when their project is registered `local-trunk`; their records and receipt mode are never rewritten.

## The standing orders, and where each is enforced

| Order | Enforced by |
| --- | --- |
| Landing is one fast check, automatic once the worker reports done, in every home | `core/trunk-landing` runs on the watcher's 30-second tick in every home (`run_fast_checks` in the watcher), so a worker's done starts the landing within seconds. It runs `jg-trunk.sh land <task>` for every `local-only` task of a local-trunk project whose status file ends with a `done` line, oldest done first, one landing at a time (a finished landing starts the next at once; two or more ready lanes land as one stack, next row), then `bin/jg-teardown.sh <task>` UNFORCED (a refusal is reported and nothing is discarded). No worker turn, lead turn or Overwatch turn. |
| Two or more queued lanes land as one stack (the merge queue) | When 2 or more lanes are ready, the landing check calls `jg-trunk.sh land-batch` for up to `batch-max` (default 5) of them, oldest done first. The lander stacks each lane onto the one before it (auto-rebase; a lane that conflicts drops out, is told with its paths, exactly as a single landing would refuse it), runs ONE gate (the lint, then the tests of the union of the stack's changed files, judged against the tip) and, on green, fast-forwards the trunk over the whole stack in one move. On red it halves the stack: the first half is judged alone and lands if green, the rest is judged on the new tip, until the lane that caused the red stands alone; only that lane is returned (`final`, reported once) and the green part lands. A single queued lane keeps the path above. Each lane keeps its own `data/trunk-landings.tsv` row (with `batch-from=<tip before the batch>`), proofs row, merged event and ticket close. The whole suite (`verify`) runs once, at the stack's top, against the trunk before the batch; a red there is traced to its one commit by halving and only that commit is reverted. Prior art: bors-ng batch-and-bisect and Kubernetes Tide batch merge (Apache-2.0; ideas only, no code copied). |
| The queue holds ready lanes until a threshold, then lands them all; `flush` and `land-next` skip the wait | The landing check does not land ready lanes one by one. It holds a project's ready lanes until `flush-at-ready` (default 3) are ready or the oldest has waited `flush-after-minutes` (default 20), then lands all of them as one stack (`batch-max` at a time, the rest at once after); both are `config/trunk-policy` keys (`flush-at-ready=1` lands every lane as soon as it is ready). `jg-trunk.sh flush <project-dir>` (Overwatch only) records `state/trunk-flush-<project>`, and the next sweep lands every ready lane now; the request ends when no ready lane is left. `jg-trunk.sh land-next <task-id>` (Overwatch only) records `state/<task>.land-next`: that lane lands at once, first in line, with the others only when the threshold is also met. A worker records neither. |
| A landing is as visible as a merge was | `land` records the same fleet-ledger `merged` event, ticket close and post-merge hook as `bin/jg-merge-local.sh`, and the check reports every landing, refusal and cleanup to the lead. The commit must carry its ticket reference (the task id or ticket key). |
| The lander rebases the lane itself; the whole proof is checked before it starts; the signature never blocks | `land` rebases the lane's one commit onto the trunk tip by itself (a clean three-way merge; the lane branch follows it, and a worktree with unsaved work is left alone), so a moved trunk is never a refusal. A branch with several commits over its base is refused. The lane keeps the head its proof is bound to until it lands, and only then follows the rebased commit. Before anything starts, the lane's own head needs its whole proof: a PASS completion receipt, approved merge-card evidence that cites files, and a sealed clean done-done run at that head holding them (`jg_dod_trunk_proof_gaps`, also run by `jg-trunk.sh proof <task>`). A PASS receipt alone is refused, and every missing input is named at once. The worker's done runs the same check, so a done that is accepted can land. A lane without its proof is left and lands by itself once the proof is complete. The owner signature is not consulted: it is recorded after the landing in `data/trunk-landing-proofs.tsv`, `absent` when missing. |
| A home's `main` moves only along the trunk | `bin/jg-home-guard.sh` installs a git `reference-transaction` hook in each home (its installer is the only writer; removing the hook is the rollback). It refuses a move of `main`, or of a detached HEAD in the home's own checkout, to a commit that is not the trunk tip, an ancestor of it, or a release merge of trunk commits (`origin/main` after the release PR merged). The live move sets `JG_TRUNK_LIVE=1` to admit a fast-forward to a newer tip and the contained re-point, and the pin-back sets `JG_TRUNK_PINBACK=1` to admit one move to the HEAD recorded before the last live move; nothing else bypasses it. |
| The trunk tip moves only by `land` | `jg-trunk.sh` installs a git `reference-transaction` hook in the project that refuses any write to the trunk branch not made by `init` or `land`; every subcommand also refuses when the branch differs from the tip `land` recorded (`state/trunk-tip-<project>`) and says so. |
| A trunk that something else moved is ended by one recorded command | The refusal `something else moved it` is class `wait` (the lane is tried again each sweep, its worker is not steered) and raises one wake per record and branch with the exact line. `jg-trunk.sh adopt-tip <project-dir> --reason <text> [--carried-by <task-id>]` (Overwatch only) records the present tip when the record is its ancestor (`forward`) or the tip is on `origin/<default>` after a fetch (`on-default`); landed commits the tip lacks are listed and refused unless `--carried-by` names a one-commit lane whose tree is the merge of the record and the tip. It keeps the old record at `refs/jg/trunk-adopted/<trunk>/<epoch>`, moves the tip record, the green pin and a stale red pin as `bin/jg-trunk.sh` documents, and writes one row to `data/trunk-adoptions.tsv`. A stored `final` for the phrase holds only while its tip record stands. |
| The trunk stays safe until its release PR lands | Nothing forces, rewrites or deletes a trunk: the project's `reference-transaction` hook refuses all three for `trunk` and every `trunk-vN`, even from `jg-trunk.sh` itself, which can only create a trunk or fast-forward it. A pin-back moves the home, never the trunk, and only to a commit that went live green (else the last release). |
| After the release merges, the next trunk is cut | `jg-trunk.sh rollover` (run by `release` and, every 5 minutes, by the landing check) refuses while the release PR is open. Once it has merged it cuts `trunk-v2` (then `-v3`, ...) from the default branch, moves the project onto it (lanes start there, landings go there) and records it in `state/trunk-branch-<project>`, `state/trunk-version-<project>` and `data/trunk-versions.tsv`. The old trunk is left exactly as it was. |
| A lane resolves its own conflicts and is never forced | The lander rebases the lane by itself. A done lane waits as it is, and the worker never rebases it or reports done again because the trunk moved; on a conflict the lander names for its lane the worker resolves it and reports ready again. The lander refuses a conflict (paths named), and `land` takes only the task id: `--force`, `-f`, `--no-verify` and any stray argument are refused and the trunk does not move. The rule is in every local-trunk lane brief and in the charter of a Squad Lead that has a local-trunk project; briefs and charters of the other three modes do not carry it. |
| The old trunk is cleaned up, unforced | After the next trunk is cut, `jg-trunk.sh retire` (run by `rollover` and the landing check) deletes the old trunk's remote branch, its local branch and any clean worktree on it, with no `--force` and a compare-and-swap ref delete. It does so only when the release it shipped is proved on the default branch AND every commit on the old trunk (every hotfix landed while the release was open) is carried into the new trunk, by ancestry or by patch. A worktree with uncommitted work, the project checkout itself, or an uncarried hotfix keeps the old trunk, and the keep is listed (once, until it changes). |
| Local gates decide landing | `land` runs the captain hold, the design, demo and nav gates, the ticket reference, the linked-decision block and owner-guard, then the lint over the changed files (`gate-lint`, default `bin/jg-lint.sh --changed-base HEAD^`), then the changed files' tests (`gate-full`, default `bin/jg-test-run.sh --required-shards HEAD^ <dir>` after the seconds-long invariants: the eight shards of the changed selection run side by side, each in its own temp directory, so the gate takes about the slowest shard rather than the sum of eight; a shard over its 10-minute wall-clock budget was slowed by the machine, so it still runs every script and is a warning, never a red, kept as one row of the machine-load ledger `data/trunk/load-<project>.tsv`, while a failed test stays a red) at the commit's exact tree in a clean clone. CI is not a landing gate. The trunk lock is held only to read the tip and to move it, never across the gates: the lane is gated on the tip it read, and the trunk moves only if it is still there. If another landing or a revert moved it meanwhile, the lane is rebased onto the new tip (a conflict refuses, with its paths) and gated again, up to three times, then waits for the next try; a stack does the same for the lanes still waiting. The default gates are Juggernaut's own suite and apply only to a repository that carries it; another project runs only the gates its home set for it (`gate-lint@<project>`, `gate-full@<project>`, `gate-verify@<project>`, with `gate-full@<project>` as its verify gate when it set no `gate-verify`), and with none set no gate runs. |
| A lane is charged only for the red it caused | When `gate-full` fails, the lander first reruns the failing scripts once on the lane, and a script that passes on that rerun is flaky and not charged: every such run is recorded in `data/trunk/flaky-<project>.tsv`, and each flaky script is filed once as its own `[blocker]` fix row (`flaky-<project>-<script>`), never a landing stop. It then reruns exactly the scripts that still fail on the trunk tip's own tree in a clean clone, in the environment the gate ended with (`gate-rerun`), and compares each script's exit status and failing test names. A script that fails the same way on the tip is the tip's red: it does not block the lane. A script that fails only on the lane, passes on the tip, or fails differently (another failing case, a changed exit status) blocks it, and so does any failure no test script accounts for. The tip's red is reported once per script and tip tree: one wake and one note on the `gate-red-ticket` ticket (default `core-self-checks-red`). The tip's result is kept by tree, so it is computed once and reused. A landing that set a red or a flaky failure aside is recorded as `full-tip-red` or `full-rerun`. A landing never moves the green pin. |
| A red found after landing is reverted by itself | After each landing the check starts `jg-trunk.sh verify <project> <commit>`: the whole suite (`gate-verify`, or `gate-full` when the home sets only that) at that commit, apart from the next landing. Verify judges what the release pull request carries: `HEAD^` in its gate names the default-branch commit the trunk version was cut from (`data/trunk-versions.tsv`), so a changed-tests gate maps every path landed since then, the same set CI maps for the release, not only the last commit's. Green moves the green pin, and so does a pass whose only failures are ones the commit's parent already had in the same way (the gate reports those once as the tip's red); a pass whose only failures passed on their rerun moves it too, with each flaky script filed as above. One verify runs at a time per project, newest wins: a verify that finds a newer commit's verify queued gives up at once, because a green result at the newer commit moves the pin over it too, and a commit strictly under the pin is not run again. A verify reads the tip without any lock and takes the trunk lock only for its short pin write, so a landing never starves it. A script that fails there and passes on the commit's parent charges that one commit: the lander lands a revert commit on the tip (the trunk only moves forward, and a commit that is itself a revert is never reverted again), then tells the lane's ticket and Overwatch, and the landing check verifies the reverted tip at once so the green pin can follow it. A run that fails with no failed test charged to a commit (a shard over its time budget, a shard with no result, a runner that stopped) is a warning and runs once more; it is never pinned and never reverted. Nothing a verify finds stops a landing: a red that stays (a revert that does not apply cleanly raises one alert; no green on the rerun is reported with the verify's own line) only leaves the green pin, and with it live, on the last green commit. |
| One alarm when the trunk has had no green for 15 minutes | Every minute the landing check runs `jg-trunk.sh green-alarm <project>`. Once the oldest commit above the green pin landed `no-green-alarm-minutes` (default 15) ago, it raises ONE alarm to Overwatch on the trunk's wake path (`jg_wake_append check`, key `trunk-no-green-<project>-<green>-stall`, which the wake routing wakes at once), naming the tip, how far it is above the last green commit and that live stays there. One alarm per green pin (`state/trunk-green-alarm-<project>`): a stall that goes on is not raised twice, and a new one after the pin moved is. |
| A refusal reaches the lane's worker and never sits silent | `core/trunk-landing/refusal-reach.sh`, called by the landing check each sweep for a lane whose current head is refused for something the worker fixes (an incomplete proof, a final refusal): a steer carrying the refusal text goes to the worker (`bin/jg-send.sh`), again every 10 minutes while the head is unchanged and the worker has no unread steer, and never for a head the lane no longer has or for a refusal that only needs time (away mode, an open decision). A refusal nobody acted on for 10 minutes raises one alert naming the lane and the refusal. The steer carries the lander's own text, which names what to run. State: `data/jg-trunk-landing/<task>.<head>.refusal`. |
| A conflicting change is fixed in the lane, never landed dirty | `land` refuses with the conflicting paths named. A done lane waits as it is; the worker acts only on a conflict the lander names for its lane (or a red its own change caused), fixes it in the lane, reports ready again, and the check lands the new head. |
| The trunk goes live only on the captain's word | `land` never moves the home. `jg-trunk.sh word live <project> "<his words>"` records the word for one commit; `jg-trunk.sh live <project>` refuses without it and spends it. A worker cannot record a word. |
| Live moves every home, from the tip's own tools | `jg-trunk.sh live` exports the tip's `bin/` and `core/` to `state/trunk-live-tool/<sha>/` and runs that copy's `bin/jg-update.sh --base <sha>`: registered Squad Lead homes first, Main last (a `state/trunk-live-restart-pending` marker for its next locked session start), one row per home; Main's registry is read from whichever home runs it, a lead home following its `.jg-squad-lead-parent` record up to Main (`bin/jg-fleet-homes-lib.sh`), so a go-live run by the lead that owns the trunk moves every home, itself included. The project's `live` row is written only when EVERY home is at the commit; otherwise the row is `hook-failed:fleet: not every home is at <sha>: <the homes>` and `autolive` tries again after `live-quiet-minutes`. A home still not at the last `live` row 10 minutes later is reported once in the landing outbox (`bin/jg-trunk-live-lag.sh`). Each home's row in `data/trunk-live.tsv` (`live`, `live,re-pointed-from:<sha>`, `live,pre-existing:<fact>`, `skipped:dirty`, `skipped:unlanded:<paths>`, `rolled-back:<reason>`). A home moves only by fast-forward, or by `reset --keep` when its HEAD is not an ancestor but the tip already holds its whole tree; a dirty home or one holding anything the tip lacks is skipped untouched, a home whose health check finds a fault it did not have before the move is pinned back (its launch overlays were refreshed and its health read first, so a fault it already had stays on the new commit as `pre-existing`), no home stops the rollout, and a pool worktree on a lane branch is never a home. `jg-trunk.sh live <project> --home <lead-home>` moves one lead only (the canary). Without `--base`, `bin/jg-update.sh` refuses a local-trunk project. |
| The go-live word can be waived per project, until the stable point | `jg-trunk.sh waiver <project> --rule <owner-rule-id>` (Overwatch only; a worker is refused) writes one line `<project> <owner-rule-id> <epoch> until=stable` to `config/trunk-live-waiver`. While that line stands, `live` for that project needs and spends no word and its row carries `waiver=<rule>`, and the landing check runs the batched `jg-trunk.sh autolive` (next row). Every project without a line keeps the word rule. Delete the line to end the waiver, once items 1-15 of the autopilot plan have landed and its load journey (item 14) is green. 
| Under a waiver the trunk goes live in batches, by itself; a red suite never does | On every tick for a project with a waiver the landing check starts `jg-trunk.sh autolive` (detached, no model turn, never holding a landing back). It moves every home to the green pin (Squad Lead homes first, Main last) once no landing has happened for `live-quiet-minutes` (default 20) or the oldest landing not yet live is `live-cap-minutes` (default 60) old, whichever comes first; both are `config/trunk-policy` keys. The outbox reports a go-live or a failed move. A landing's own suite (`verify`) runs apart from this: `autolive` moves only to the green pin, so a red commit (reverted, or left below a pin that did not move) is never live, and landings never wait for it. A commit already live is not moved again, and with no waiver `autolive` does nothing, so the word rule stands. A red CI (`ci red`) pins EVERY home back to the last green live commit at once (`live,pinned-back-from:<sha>`; a dirty home is skipped, never forced). |
| The release is the trunk going into main as ONE pull request, on his word | `jg-trunk.sh release` carries the last green commit (`state/trunk-green-<project>`), never the tip, so landings that keep moving the tip cannot hold a green release back; the commits after the pin wait for their own green. It refuses without a recorded `release` word for that commit (`word release` records it) and while no commit has passed the full suite. It pushes that commit to the trunk branch (never forced) and opens one pull request from the trunk itself into the default branch. There is no release branch. While that pull request is open, a later release only pushes the new commits into it. The pull request is recorded under its own task, `release-<project>-<trunk>` (no worker, `yolo=off`), through `bin/jg-pr-check.sh`, whose guard admits the project's current trunk as the release head (`jg_is_release_head` in `bin/jg-version-branch-lib.sh`) and refuses every other head into the default branch; it merges with a merge commit through an explicit `bin/jg-pr-merge.sh release-<project>-<trunk> <url>`. |
| No feature pull requests | The only pull request is the release one. Lanes ship `local-trunk`; legacy `local-only` contracts remain accepted, and PR modes are refused. |
| CI runs after live; a red CI pins back | `jg-trunk.sh ci <project> <sha> red` moves the green pin, and every home, back to the newest earlier commit that went live and was not red (else the last release); landings go on. `ci ... green` records the result and advances the green pin. `release` ships only the green pin. |

## Lifecycle of one ticket

1. The lane starts on the trunk tip, makes one commit, runs the light gate over its changed files and reports ready with its `done` line.
2. The `trunk-landing` check lands it on the trunk by itself: it rebases the commit onto the tip, lints the changed files, runs the changed files' tests against the tip's own result, and reports `landed`. Three lanes ready together (the `flush-at-ready` threshold), or the oldest one waiting `flush-after-minutes`, land in the order they reported done, as one stack behind one gate. If it refuses, the report names the reason once (a conflict names its paths); the lane fixes it and reports ready again. A refusal that only needs time (away mode, an open linked decision) retries on its own; a red trunk is never one.
3. The whole suite then runs at the landed commit. Green moves the green pin; a red that commit caused reverts it by itself and tells the lane; a failure with no failed test runs once more and is never charged. Landings never stop for a red, and the trunk with no green for 15 minutes raises one alarm.
4. On the captain's word: `jg-trunk.sh word live`, `live`.
5. On the captain's word: `word release`, `release`. CI runs on the pushed trunk; a red result goes to `jg-trunk.sh ci`.
6. When the release PR merges, the next trunk version is cut from the default branch and the cycle starts again on it; the old trunk is cleaned up once everything on it is carried.

## Moving a home onto the trunk

The lander takes one commit, so a home whose `main` carries the same changes under other SHAs is not an ancestor of the trunk. It moves anyway, and only after proof: `bin/jg-home-contained.sh <home-head> <trunk-tip>` exits 0 when every path the home changed is byte-identical at the tip or was changed later by a trunk commit, and exits 1 listing the uncontained paths. With a clean working tree and that exit 0, the home moves by `git reset --keep <trunk-tip>`; never a merge, stash or force. The mover is slice T2.

## Records

`state/trunk-tip-<project>`, `trunk-green-<project>`, `trunk-green-alarm-<project>`, `trunk-released-<project>`, `trunk-word-<live|release>-<project>`; `data/trunk-landings.tsv` (one row per lane; a stacked lane adds `batch-from=<sha>`), `trunk-landing-proofs.tsv` (the seal, merge-card and signature each landing had, and `gate=ran:<scripts>,failed:<on the first run>,secs:<whole gate>`, which the landing's Evidence card prints), `trunk/tip-results-<project>-<tree>.tsv` and `trunk/tip-red-reported-<project>.tsv` (the tip baseline and what was reported), `trunk-live.tsv`, `trunk-ci.tsv`, `trunk-words.tsv`, `trunk-releases.tsv`; the check's own state in `data/jg-trunk-landing/`.

## Tests

The `bin/jg-trunk.sh` suites (run by the done-done journey `trunk-landing`, over the shared `tests/jg-trunk-fixture.sh`) fail when any behaviour above is removed: `tests/jg-trunk.test.sh` owns landing, release, the trunk's safety and a refusal reaching the worker; `tests/jg-trunk-gate.test.sh` the landing gate, the proof and the journey of three lanes landing in order, a red lane refused and a post-land red reverted; `tests/jg-trunk-queue.test.sh` the merge queue and its threshold, `flush` and `land-next` (one stack, a conflict dropping out, a red stack halved to its guilty lane, a post-batch red traced to one commit); `tests/jg-trunk-retry.test.sh` how a refused landing is classed wait, retry or final and the retry of a refusal the machine caused (2 minute backoff, 3 tries, then final with one report); `tests/jg-trunk-verify.test.sh` verify (a pass on the rerun moves the pin and files one row per flaky test; a red with no failed test never pins, and a ready lane lands on it with no hand step; the no-green alarm is raised once) and the trunk lock. `tests/jg-update-local-base.test.sh` owns the fleet move and the waiver; `tests/jg-trunk-live.test.sh` owns the registered check and the automatic live step (the quiet window and the hourly cap move every home, a red suite never does, a red CI pins every home back).
