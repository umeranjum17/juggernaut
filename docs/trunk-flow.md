# Trunk flow

How a change reaches the captain's users, for every project registered `local-trunk`, in every home. `bin/jg-trunk.sh` owns each step; its header is the command reference, and `bin/jg-trunk-policy-lib.sh` holds every open captain call with its safe default (override in `config/trunk-policy`).

## Scope: local-trunk projects only

The trunk flow is a fourth delivery posture, `local-trunk` (`data/projects.md`: `- <name> [local-trunk] - ...`). **Every rule below applies to a project registered local-trunk and to no other.** A project registered `no-mistakes`, `direct-PR` or `local-only` (or not registered) keeps its own rules exactly as before: `direct-PR` still pushes and opens its PR, `no-mistakes` still runs its pipeline, `local-only` still stops at a ready branch and is merged locally by `bin/jg-merge-local.sh`. Each trunk entry point reads the project's registered mode first and refuses or ignores any other: every `jg-trunk.sh` subcommand refuses it naming the registered mode, the landing check skips it, the spawn refusal and the lane brief section apply only to local-trunk, and no trunk hook is installed in it. `tests/jg-trunk-scope.test.sh` proves one case per mode and fails if any of them is treated as local-trunk.

In a local-trunk project the lanes ship as `local-trunk` tasks (nothing is pushed), and both normal and `--raw` output from `bin/jg-project-mode.sh` retain `local-trunk`.
Pass `--mode local-trunk` to the brief, spawn and Recon promotion; the generated delivery contract, recorded task mode and completion receipt retain that identity.
Existing in-flight `mode=local-only` tasks remain accepted by the trunk lander and landing check only when their project is registered `local-trunk`; their records and receipt mode are never rewritten.

## The standing orders, and where each is enforced

| Order | Enforced by |
| --- | --- |
| Landing is one fast check, automatic once the worker reports done, in every home | `core/trunk-landing` runs on the watcher's 30-second tick in every home (`run_fast_checks` in the watcher), so a worker's done starts the landing within seconds. It runs `jg-trunk.sh land <task>` for every `local-only` task of a local-trunk project whose status file ends with a `done` line, oldest done first and one at a time (a finished landing starts the next at once), then `bin/jg-teardown.sh <task>` UNFORCED (a refusal is reported and nothing is discarded). No worker turn, lead turn or Overwatch turn. |
| A landing is as visible as a merge was | `land` records the same fleet-ledger `merged` event, ticket close and post-merge hook as `bin/jg-merge-local.sh`, and the check reports every landing, refusal and cleanup to the lead. The commit must carry its ticket reference (the task id or ticket key). |
| The lander rebases the lane itself; the seal, the merge-card and the signature never block | `land` rebases the lane's one commit onto the trunk tip by itself (a clean three-way merge; the lane branch follows it, and a worktree with unsaved work is left alone), so a moved trunk is never a refusal. A branch with several commits over its base is refused. The done-done receipt, the merge-card and the owner signature are not consulted: what exists is recorded after the landing in `data/trunk-landing-proofs.tsv`, what is missing is recorded as `absent`, and nothing is refused or redone for it. |
| A home's `main` moves only along the trunk | `bin/jg-home-guard.sh` installs a git `reference-transaction` hook in each home (its installer is the only writer; removing the hook is the rollback). It refuses a move of `main`, or of a detached HEAD in the home's own checkout, to a commit that is not the trunk tip, an ancestor of it, or a release merge of trunk commits (`origin/main` after the release PR merged). The live move sets `JG_TRUNK_LIVE=1` to admit a fast-forward to a newer tip and the contained re-point, and the pin-back sets `JG_TRUNK_PINBACK=1` to admit one move to the HEAD recorded before the last live move; nothing else bypasses it. |
| The trunk tip moves only by `land` | `jg-trunk.sh` installs a git `reference-transaction` hook in the project that refuses any write to the trunk branch not made by `init` or `land`; every subcommand also refuses when the branch differs from the tip `land` recorded (`state/trunk-tip-<project>`) and says so. |
| The trunk stays safe until its release PR lands | Nothing forces, rewrites or deletes a trunk: the project's `reference-transaction` hook refuses all three for `trunk` and every `trunk-vN`, even from `jg-trunk.sh` itself, which can only create a trunk or fast-forward it. A pin-back moves the home, never the trunk, and only to a commit that went live green (else the last release). |
| After the release merges, the next trunk is cut | `jg-trunk.sh rollover` (run by `release` and, every 5 minutes, by the landing check) refuses while the release PR is open. Once it has merged it cuts `trunk-v2` (then `-v3`, ...) from the default branch, moves the project onto it (lanes start there, landings go there) and records it in `state/trunk-branch-<project>`, `state/trunk-version-<project>` and `data/trunk-versions.tsv`. The old trunk is left exactly as it was. |
| A lane resolves its own conflicts and is never forced | The lander rebases the lane by itself. On a conflict the worker resolves it and reports ready again. The lander refuses a conflict (paths named), and `land` takes only the task id: `--force`, `-f`, `--no-verify` and any stray argument are refused and the trunk does not move. The rule is in every local-trunk lane brief and in the charter of a Squad Lead that has a local-trunk project; briefs and charters of the other three modes do not carry it. |
| The old trunk is cleaned up, unforced | After the next trunk is cut, `jg-trunk.sh retire` (run by `rollover` and the landing check) deletes the old trunk's remote branch, its local branch and any clean worktree on it, with no `--force` and a compare-and-swap ref delete. It does so only when the release it shipped is proved on the default branch AND every commit on the old trunk (every hotfix landed while the release was open) is carried into the new trunk, by ancestry or by patch. A worktree with uncommitted work, the project checkout itself, or an uncarried hotfix keeps the old trunk, and the keep is listed (once, until it changes). |
| Local gates decide landing | `land` runs the captain hold, the design, demo and nav gates, the ticket reference, the linked-decision block and owner-guard, then the lint over the changed files (`gate-lint`, default `bin/jg-lint.sh --changed-base HEAD^`), then the changed files' tests (`gate-full`, default `bin/jg-test-run.sh --changed --base HEAD^` after the seconds-long invariants) at the commit's exact tree in a clean clone. CI is not a landing gate. |
| A lane is charged only for the red it caused | When `gate-full` fails, the lander first reruns the failing scripts once on the lane, and a script that passes on that rerun is flaky and not charged. It then reruns exactly the scripts that still fail on the trunk tip's own tree in a clean clone, in the environment the gate ended with (`gate-rerun`), and compares each script's exit status and failing test names. A script that fails the same way on the tip is the tip's red: it does not block the lane. A script that fails only on the lane, passes on the tip, or fails differently (another failing case, a changed exit status) blocks it, and so does any failure no test script accounts for. The tip's red is reported once per script and tip tree: one wake and one note on the `gate-red-ticket` ticket (default `core-self-checks-red`). The tip's result is kept by tree, so it is computed once and reused. A landing that set a red or a flaky failure aside is recorded as `full-tip-red` or `full-rerun`. A landing never moves the green pin. |
| A red found after landing is reverted by itself | After each landing the check starts `jg-trunk.sh verify <project> <commit>`: the whole suite (`gate-verify`) at that commit, apart from the next landing. Green moves the green pin. A script that fails there and passes on the commit's parent charges that one commit: the lander lands a revert commit on the tip (the trunk only moves forward, and a commit that is itself a revert is never reverted again), then tells the lane's ticket and Overwatch. A red nobody can charge to one commit, or a revert that does not apply cleanly, writes the red pin: landings stop except a `fixes-red` commit. |
| A conflicting change is fixed in the lane, never landed dirty | `land` refuses with the conflicting paths named. The lane rebases onto the trunk tip, fixes the conflict, reports ready again, and the check lands the new head. |
| The trunk goes live only on the captain's word | `land` never moves the home. `jg-trunk.sh word live <project> "<his words>"` records the word for one commit; `jg-trunk.sh live <project>` refuses without it and spends it. A worker cannot record a word. |
| The release is the trunk going into main as ONE pull request, on his word | `jg-trunk.sh release` refuses without a recorded `release` word for the tip. It pushes the trunk (never forced) and opens one pull request from the trunk itself into the default branch. There is no release branch. While that pull request is open, a later release only pushes the new commits into it. |
| No feature pull requests | The only pull request is the release one. Lanes ship `local-trunk`; legacy `local-only` contracts remain accepted, and PR modes are refused. |
| CI runs after live; a red CI pins back | `jg-trunk.sh ci <project> <sha> red` writes the red pin, stops landings except a commit with `fixes-red: <sha>`, and moves the home back to the newest earlier commit that went live and was not red (else the last release). `ci ... green` records the result and advances the green pin. |

## Lifecycle of one ticket

1. The lane starts on the trunk tip, makes one commit, runs the light gate over its changed files and reports ready with its `done` line.
2. The `trunk-landing` check lands it on the trunk by itself: it rebases the commit onto the tip, lints the changed files, runs the changed files' tests against the tip's own result, and reports `landed`. Three lanes ready together land in the order they reported done. If it refuses, the report names the reason once (a conflict names its paths); the lane fixes it and reports ready again. A refusal that only needs time (away mode, an open linked decision, a red trunk) retries on its own.
3. The whole suite then runs at the landed commit. Green moves the green pin; a red that commit caused reverts it by itself and tells the lane.
4. On the captain's word: `jg-trunk.sh word live`, `live`.
5. On the captain's word: `word release`, `release`. CI runs on the pushed trunk; a red result goes to `jg-trunk.sh ci`.
6. When the release PR merges, the next trunk version is cut from the default branch and the cycle starts again on it; the old trunk is cleaned up once everything on it is carried.

## Moving a home onto the trunk

The lander takes one commit, so a home whose `main` carries the same changes under other SHAs is not an ancestor of the trunk. It moves anyway, and only after proof: `bin/jg-home-contained.sh <home-head> <trunk-tip>` exits 0 when every path the home changed is byte-identical at the tip or was changed later by a trunk commit, and exits 1 listing the uncontained paths. With a clean working tree and that exit 0, the home moves by `git reset --keep <trunk-tip>`; never a merge, stash or force. The mover is slice T2.

## Records

`state/trunk-tip-<project>`, `trunk-green-<project>`, `trunk-red-<project>`, `trunk-released-<project>`, `trunk-word-<live|release>-<project>`; `data/trunk-landings.tsv`, `trunk-landing-proofs.tsv` (the seal, merge-card and signature each landing had), `trunk/tip-results-<project>-<tree>.tsv` and `trunk/tip-red-reported-<project>.tsv` (the tip baseline and what was reported), `trunk-live.tsv`, `trunk-ci.tsv`, `trunk-words.tsv`, `trunk-releases.tsv`; the check's own state in `data/jg-trunk-landing/`.

## Tests

`tests/jg-trunk.test.sh` (run by the done-done journey `trunk-landing`) fails when any behaviour above is removed, including the journey of three lanes landing in order, a red lane refused and a post-land red reverted.
