# Landing conflict resolving

Landing conflict resolving: run `done-done run -- bash -c 'r=DONE_DONE_EVIDENCE_ROOT; bash bin/jg-test-run.sh tests/jg-trunk-resolve.test.sh tests/jg-trunk-retest.test.sh tests/jg-trunk.test.sh > "${!r}/resolving.log" 2>&1'`; the real `bin/jg-trunk.sh land` over fixture homes proves that a rebase that meets a conflict in one file goes to the landing run state `resolving`, that the resolver the home set (policy `conflict-resolver`) resolves it in the lander's own copy, that the touched file is listed on the run (`data/trunk-resolving.tsv`), that `conflict_at` is written on the ticket, that the lane lands as one commit and no steer goes to its worker, that a resolver that gives up or passes `conflict-limit-seconds` ends the run `returned` with the reason and leaves the trunk where it was, that with no resolver set the conflict is refused as before, and (slice J32b) that after a resolution the run goes to `retesting`: the runner (policy `retest-runner`, else `done-done verify --affected-by`) is handed the touched files, runs only the affected journeys on the rebased commit and prints their count, the receipt names that commit and the one it extends, a journey red on the commit ends the run `returned` with `returned_at` written, and a runner that stops three times leaves the ticket in delivering on the wait `lead` (reason `blocker`) with no steer to the worker (screen: none).
