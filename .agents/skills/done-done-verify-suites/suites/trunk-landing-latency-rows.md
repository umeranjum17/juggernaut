Trunk landing latency: run `done-done run trunk-latency` (which runs `bash tests/jg-trunk-latency.test.sh` and `bash tests/jg-trunk-queue-why.test.sh`, and writes `trunk-latency.log` and the `land` payload of its first landing as `trunk-latency.json` into `$DONE_DONE_EVIDENCE_ROOT`); on a fixture home's ticket tables the real `core/trunk-latency/latency.sh` measures the records of two landings of 9 and 10 Nov, each is recorded as the ticket's `land` event, and the check at the clock of each proves the 32-minute landing raises one alert that names the queue and its minutes from the payload, the 2-minute landing raises none, a third tick adds none, the limit is `JG_MERGE_LATENCY_LIMIT_MINUTES`, an old landing raises no alert, a landing whose event is not there yet is read on a later tick, the wiring's installed shim runs the check, and no `data/trunk-latency.tsv` is written (screen: none).

Run `done-done run trunk-landing` to prove the real landing records the done epoch before cleanup removes the lane status file and writes no latency file; `tests/jg-trunk-gate.test.sh` drives this journey and the run captures its result in `run.log` (screen: none).
